# The live windows test waits on wall time for the demo stream

## Summary

The end-to-end test that checks the live windows after a reload failed now and then on the macOS runner.
It waited ten seconds of real time for six seconds of demo data.
The demo meter makes its samples per timer tick, so a slow runner gets less data in the same real time.
Now the test runs the page clock itself and waits for the data, so a slow runner can no longer fail it.

## Requirement

### Steps to reproduce
1. Run the reload spec's live-window test on a loaded macOS runner.

### Expected
The test passes whatever the runner's speed.

### Actual
"Expected: >= 6, Received: 5" at the wait for the stats clock (CI run 42773524151, macOS, chromium).

## Acceptance Criteria

- AC-3B70S3.1: Regression: the live-window reload test holds the page clock and steps it until the statistics clock reads at least 6 s; no wait in the test depends on how fast the runner's wall clock moves.
- AC-3B70S3.2: After the reload, each window (10 s, 1 min, 10 min, then 10 s again) must show the backfilled history within 1.5 s of page time, stepped on the held clock, with the same window checks as before.
- AC-3B70S3.3: The test passes 20 runs in a row locally on WebKit and on Chromium with one worker.

## Technical Design

### Root cause
The mock demo meter emits samples per 25 ms timer tick, not per elapsed time, so session time lags wall time on a throttled runner and the 10 s wall-clock poll for 6 s of session time runs out.

### Fix
Hold the clock with the shared helper and step it in slices with the shared stepper until the stats clock reaches 6 s, then reload and step until each window passes its check, with a page-time limit in place of the CI latency budget.

## Testing

The reload spec repeated 20 times with one worker on WebKit and Chromium.
