# Firmware flashing engine

## Summary

This feature updates the meter's application firmware from a local file.
It switches the meter into its bootloader and sends the file as the vendor tool does.
Then it checks the result.
The bootloader itself is never written, so a failed update can always be retried from bootloader mode.
Nothing is retried automatically, and every step reports its progress and any error clearly.

## Requirement

The library and the command line tool flash a verified firmware container onto the meter's application area through the bootloader, report progress and errors, verify the new version afterwards, and never write the bootloader or retry without the user.

## Acceptance Criteria

- AC-V9SK54.1: From application mode the library first opens a session the way the vendor tool does (CONNECT, the UID read, 0x4C authentication at level 1), then sends JUMP_DFU and reports the meter's reply to it. A failed authentication stops before JUMP_DFU is sent. If the meter does not restart by itself, the library asks the user to unplug it and plug it back in, then waits up to two minutes for bootloader mode. If it is still not in bootloader mode after the wait, it stops and explains the hold-Back-and-plug-in fallback.
- AC-V9SK54.2: In bootloader mode the library runs the documented sequence: CONNECT, HEAD (field must be zero), the 0x42 descriptor with start 0x4000, end, size, CRC, model, version and date, the erase wait with its tolerant timeouts, the payload in 4080-byte writes each acknowledged by SYNC, and FINISHED. Each failure maps to its own typed error.
- AC-V9SK54.3: The start address is always 0x4000, and the library refuses any descriptor that would write below it.
- AC-V9SK54.4: Progress is reported as stages (switch, erase, write with bytes done, verify, finished) for the CLI and the desktop app.
- AC-V9SK54.5: After FINISHED the library sends JUMP_APROM. If the meter does not come back in application mode by itself, it asks the user to unplug the meter and plug it back in, and waits for that. It then reads the application info block to confirm the new version, or ends with a power-cycle prompt if the meter never comes back.
- AC-V9SK54.6: There is no automatic retry. After any failure the meter is left in bootloader mode with a message on how to retry.
- AC-V9SK54.7: The command line tool's firmware flash command needs an explicit acknowledgement flag and refuses files that fail inspection. Its first line names the image size the file declares.
- AC-V9SK54.8: The simulator emulates the bootloader (mode switch, erase, write, verify, and injected failures at each step), and every failure path is tested against it.
- AC-V9SK54.9: Between modes the library finds the meter again by its USB serial, which is the same in application and bootloader mode. Without a chosen serial it keeps to the serial of the meter it first opened, and it never picks another meter.

## Technical Design

A flash session in the protocol crate drives the bootloader over bulk with the vendor's timeouts. The steps form a state machine that emits progress events. Every write-capable command is reachable only through this session, behind the acknowledgement.

## Testing

Simulator tests for the happy path and an injected failure at each step, a property test for the 0x4000 floor, and CLI tests for the acknowledgement. Hardware runs follow the staged plan FR.

## Notes

JUMP_DFU, JUMP_APROM, 0x42 and payload writes are forbidden on the real meter until the user approves each stage.

Real meter, 2026-10-26: a jump takes effect at the next power-up, so AC .1 and .5 ask for a replug. The bootloader ignores the first CONNECT, so one unanswered CONNECT is retried; the flash itself never is.
