# build:wasm picks a Rust without the wasm target

## Summary

The web edition's module build failed on a Mac where a Homebrew Rust comes before rustup on the search path.
That Rust has no WebAssembly target, so the build stopped with a confusing compiler error.
The build now runs cargo through rustup with the project's pinned toolchain when rustup is installed, and otherwise checks for the target first and says how to fix it.

## Requirement

### Steps to reproduce
1. Put Homebrew rustc 1.96 before the rustup shims on the PATH.
2. Run the wasm build script.

### Expected
The build uses the toolchain pinned in the repository, or fails with a message naming the missing target and the fix.

### Actual
cargo from Homebrew runs and fails because the wasm32 target is not installed (web HIL notes, 2026-11-08).

## Acceptance Criteria

- AC-G30K4S.1: When rustup is on the PATH, the wasm build runs cargo as rustup run with the channel read from the repository's rust toolchain file, so a different cargo earlier on the PATH is not used.
- AC-G30K4S.2: When rustup is not on the PATH and the active rustc does not list the wasm32-unknown-unknown target as installed, the build stops before cargo with a message naming the target and the rustup command that adds it.
- AC-G30K4S.3: Regression: the script's command choice is unit-tested for both cases, failing before the fix and passing after it.

## Technical Design

### Root cause
The script called the bare cargo on the PATH, which bypasses the rustup pin when another Rust shadows it.

### Fix
Read the channel from the toolchain file and build through rustup run, with RUSTC pinned to that toolchain (rustup run alone still lets cargo spawn the first rustc on the PATH); without rustup, probe the sysroot for the target and fail clearly.

## Testing

A Vitest test over the script's pure command-picking function.

## Notes

Developer tooling only; CI already uses rustup.
