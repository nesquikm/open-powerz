# The desktop app cannot open a recording given at launch

## Summary

A recording can only be opened through the Open recording dialog.
Now the desktop app also opens a recording named on its command line.
On macOS it also opens one that Finder hands it, so Open With works.
The file opens straight into the File tab, the same way the dialog does.
Nothing is sent to a meter.

## Requirement

The desktop app takes a recording path at launch, or from the operating system while it runs, and opens it in the File tab.

## Acceptance Criteria

- AC-M078V5.1: Launching the desktop app with a CSV or vendor `.db` path as an argument opens that file in the File tab at startup, with no dialog.
- AC-M078V5.2: An argument that is not an existing CSV or `.db` file is ignored; the app starts as usual.
- AC-M078V5.3: On macOS, a file the system hands the app, at launch or while it runs, opens in the File tab the same way; the bundle declares CSV and `.db` as files it can open, without becoming their default app.
- AC-M078V5.4: A file opened this way follows the same rules as Open recording: a refused file shows the same error, and an open file is replaced only when the new one has been read.
- AC-M078V5.5: The web edition is unchanged.

## Technical Design

The backend picks the first argument that names an existing CSV or `.db` file, and also takes paths from the macOS open-file event, as a pending launch file. A new command opens the pending file through the same reader as Open recording. On macOS a running app also gets an event to pick it up. At startup, and on that event, the frontend asks for the pending file and shows the File tab when one opens. The bundle lists CSV and `.db` with an alternate rank, so the app is never their default.

## Testing

Rust unit tests cover the argument and path rules. Vitest covers the backend call and the store. A Playwright spec on the mocked backend opens a launch file into the File tab.
