# Replug reconnects to the meter

## Summary

After a real unplug and replug, the app fell back to the demo device.
The user had to reconnect the meter by hand, and no gap band was shown.
Now the meter stays selected while it is away and reconnects on its own.
The session goes on with a No data band over the gap.
A running recording still ends cleanly at the unplug.

## Requirement

When the connected meter is unplugged and plugged back in, the app reconnects to that same meter without user action and continues the session with the gap marked.

### Steps to reproduce

1. Connect a real meter and stream at 1000 SPS.
2. Unplug the meter's data cable, wait a few seconds, and plug it back in.

### Expected

The meter stays selected, the app reconnects to it within 3 s, and the session continues with a No data band over the gap.

### Actual

The picker switches to a demo device, the meter must be chosen and connected again by hand, and no gap band is shown.

## Acceptance Criteria

- AC-TGE839.1: Regression: when the connected meter is unplugged, the device picker keeps that meter selected and the top bar shows a disconnected, waiting state for it. The app never selects or connects a demo device on its own.
- AC-TGE839.2: When a meter with the same serial is listed again by the OS, the app reconnects to it within 3 s without user action and streaming resumes at the rate that was selected before.
- AC-TGE839.3: After the reconnect the session continues on the same timeline. The time between the last sample before the unplug and the first sample after it shows as a No data band in the live chart, in Whole session and in the CSV export.
- AC-TGE839.4: A meter with a different serial that appears while the app waits is listed but not connected automatically.
- AC-TGE839.5: Choosing a demo device by hand still works while a meter is away, and cancels the wait for that meter.
- AC-TGE839.6: A recording that is running at the unplug ends within 2 s of the last sample, its file is complete, and a notice says it ended because the meter was disconnected.
- AC-TGE839.7: On the real meter, an unplug and replug while streaming at 1000 SPS reconnects within 3 s and shows the gap band. The result is recorded in the Notes.

## Technical Design

### Root cause

A device list without the selected meter reset the selection to the first entry (the `devices[0]` fallback in `session.svelte.ts`), which is a demo device once the meter is gone. Nothing reconnected a meter that came back.

### Fix

The device manager remembers the awaited serial. The hotplug watcher matches listings by serial and reuses the connect path and per-serial store, so the existing gap logic applies; it re-reports the list each poll while waiting. A manual pick cancels the wait. A picked meter that vanishes while its session runs, ended with an error or is awaited stays listed and picked, whichever event arrives first.

## Testing

Worker integration tests with the simulator unplugging and replugging a meter by serial, including a second serial and a manual demo choice. Vitest for picker state. A Playwright test on the mocked backend for the waiting state and the gap band. The real-meter check is manual.

## Notes

Follows the failed replug half of AH2AEN.10 on build 55c7b88: the session fell back to the demo device and needed a manual reconnect.

AC.7 on the real meter, 2026-10-23, 1000 SPS: reconnect 140 ms after relisting, gap recorded. An earlier run missed an unplug; cause unknown (plan follow-up).

## Implementation notes

- DevicePicker.svelte: cancel_wait is a separate async IPC call, so a replug landing in the milliseconds between the pick and that call could still reconnect the meter — window is a few ms of user action; accepted
- tests/replug.rs asserts wall-clock bounds (reconnect <= 3 s, recording stop <= 2 s) — the bounds are the ACs themselves and the sim reconnect is near-instant; watch CI for flakes
- tests/replug.rs leaves its temp dirs behind when an assertion fails — test-only hygiene; directories are per-pid under the OS temp dir
- a reconnect whose open keeps failing (EBUSY, permissions) retries every 500 ms poll and re-sends disconnected/waiting statuses each time — keeps waiting as the AC asks; a back-off is an M7 polish item
- a real meter whose session errors before its first sample is not awaited (no outage), so it is not reconnected — never streamed, so the unplug wording of AC.1 does not apply; the UI still keeps it picked
- recording notice reads 'the meter was unplugged', not the literal word 'disconnected' — same meaning; wording predates this FR and has its own test
