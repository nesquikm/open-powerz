# Firmware file inspection

## Summary

Firmware for the meter comes as an encrypted container file from the vendor's download page.
This feature reads the container's header and shows what is inside: model, version, date, size, checksum and the release notes.
A file for another model or a broken file is refused before anything touches the meter.
The app never decrypts the firmware and never ships firmware files.

## Requirement

The library, the command line tool and the desktop app parse a local firmware container, show its metadata and refuse files that are corrupt or for another model, without decrypting the image.

## Acceptance Criteria

- AC-V9SK53.1: The parser reads the container header (magic, vendor, container version, model, firmware version, date, CRC, size and both release notes) and the encrypted payload, following the documented layout.
- AC-V9SK53.2: A wrong magic, a truncated file, a payload shorter than the declared size, or a model that differs from the connected meter is refused with a clear reason before any device command is sent.
- AC-V9SK53.3: The command line tool's firmware info command prints the metadata, and the desktop app shows it with the English release notes.
- AC-V9SK53.4: No input makes the parser panic (property test), and the tests use synthetic containers built by the test suite; no vendor firmware file is committed.
- AC-V9SK53.5: The parser never decrypts or changes the payload; it is passed on byte for byte.

## Technical Design

A container module reads the big-endian Qt data stream: a count, then length-prefixed UTF-16 strings, then a length-prefixed byte array. A builder used only by tests writes synthetic containers.

## Testing

Unit and property tests for the parser, builder round trips, and a check against the real 2.0.7 file kept outside the repo, run by hand.

## Notes

The vendor file in the research workspace is read only; it is never copied into the repo.
