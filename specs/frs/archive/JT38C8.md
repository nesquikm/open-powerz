# A meter on the old bootloader (2.1) shows as unknown

## Summary

A Linux user's KM003C runs bootloader 2.1, an older generation than the 2.5 on our own meter.
In its bootloader it shows one vendor interface named after the product and no HID interface.
The app and the command line called that mode unknown, so nobody could tell what the meter was doing.
Now that shape is recognised as an old bootloader, and every place that names the mode says so.
Bootloader 2.5 and application mode are classified exactly as before.

## Requirement

### Steps to reproduce
1. Put a KM003C with bootloader 2.1 into its bootloader (hold Back while it is off, then plug it in).
2. Run `powerz devices` and `powerz firmware probe`, or open the desktop device list.

### Expected
The meter is named as being in an old bootloader that is not supported yet.

### Actual
`Mode: unknown`; the desktop lists it with no mode at all.

## Acceptance Criteria

- AC-JT38C8.1: Regression: a POWER-Z device whose vendor-class (0xFF) interface has a string that is neither `APP` nor names `boot` or `dfu` (any case), and that has no HID (0x03) interface, is classified as the old bootloader. The field-reported 2.1 descriptor (one interface, class 0xFF, subclass 0xFF, string `POWER-Z KM003C`) classifies so both from the device-list entry and from the full USB identity.
- AC-JT38C8.2: The 2.5 bootloader shape (interface 0 class 0xFF subclass 0x00 `BOOT`, CDC 0x02 `BOOT`, 0x0A) still classifies as bootloader, the application shape (`APP` vendor, CDC, CDC data, HID) as application, and a vendor interface without a string stays unknown; all four shapes are pinned in tests built from descriptor fixtures.
- AC-JT38C8.3: The simulator has an old-bootloader persona with the 2.1 descriptor that answers neither CONNECT nor HEAD, selected with `POWERZ_SIM_MODE=legacy-bootloader` for `firmware probe`, `flash` and `jump` on the demo device.
- AC-JT38C8.4: Everywhere the CLI names a meter's mode (`devices`, `firmware probe`, text and JSON), the old bootloader reads `bootloader (old, not supported yet)` in text and `legacy_bootloader` in JSON.
- AC-JT38C8.5: The desktop device list labels such a meter `(old bootloader, not supported yet)`, and Connect refuses it before opening anything with a message saying to unplug and replug the meter to return to the application firmware; the web UI's mode type and the mock backend carry the new mode.
- AC-JT38C8.6: The in-repo protocol spec states the vendor app's mode rule (string index 2: `APP` is application, anything else a bootloader) `[static]`, the 2.1 bootloader descriptor from the field report `[device]`, that the vendor WinUSB INF also binds the whole non-composite 0x0063 device `[static]`, and our classification rule.

## Technical Design

### Root cause
`DeviceMode::from_interface_string` knows only `APP` and strings naming boot/dfu; the 2.1 string is the product name.

### Fix
New `DeviceMode::LegacyBootloader` (name `legacy_bootloader`), so every exhaustive match must handle it. Classification takes the vendor string plus whether a HID interface exists and the vendor subclass; `DeviceEntry` gains those fields from the OS list (still nothing opened). Sim: `Persona::LegacyBootloader` identity and silent bulk pipe. Desktop: `mode_suffix`, `ensure_connectable`, TS `DeviceMode`, mock listing.

## Testing

Unit tests on the classifier over the four descriptor fixtures; sim persona test; CLI integration tests for text and JSON mode; backend test for the label and the Connect refusal; Vitest for the TS label.

## Notes

Field report: app 1.9.5, bootloader 2.1, Linux AppImage v0.13.1. Mtools reads string index 2 only; listing never opens the device, so we use the vendor interface string, which is index 2's text on both known shapes.

## Implementation notes

- `DeviceMode::LegacyBootloader` is classified from the vendor string plus `has_hid`; `vendor_subclass` is stored on the entry but not used in the decision.
- The CLI has no `devices` command: AC .4 is met through `firmware probe` and `info`, the two commands that name a mode.
- Not checkable on our 2.5 meter; the 2.1 shape is pinned by fixtures and the simulator persona.
