# Logo writes change the startup duration and leave the settings check stale

## Summary

The meter showed that the logo flag write really sets the startup screen duration.
Upload sets it to 3 seconds, and Remove turns the startup screen off.
After that write the meter keeps an old check value on its settings.
Our reader then refuses them until the user saves a setting in the meter's menu.
The tools now warn before the write, then show the menu steps and wait.
The simulator models the stale check and its repair.

## Requirement

### Steps to reproduce
1. On a KM003C with the startup duration at 5 s, run a logo write with confirmation, then read the settings.
2. Run a logo remove, then read the settings.

### Expected
The tool says before the write that Upload sets 3 s and Remove turns the startup screen off. Afterwards it reports the duration the meter really has, and when the settings need a save in the meter's menu it says how to do that and waits for it.

### Actual
M7C stage 2 and 3 reports, 2026-11-06: the upload moved the duration from 5 s to 3 s without warning; the settings read then failed with "SETTINGS block A: CRC mismatch" (exit 5) until a menu save. After Remove the tool printed "Startup: 3 s" while the meter was at Disable.

## Acceptance Criteria

- AC-Z39H24.1: Regression: in the simulator a SET_DATA 0x1C write of 2 sets the startup duration bits (bits 14–15 of the settings word at 0x00) to 3 s and of 0 to off, and the next SETTINGS reply keeps the block A check value from before the write, so the typed settings decode fails.
- AC-Z39H24.2: The simulator's menu save sets a duration of the user's choice and makes block A valid again with every other byte unchanged; until then every SETTINGS reply stays stale.
- AC-Z39H24.3: Regression: after an upload or Remove the result carries the duration before the write, the duration the write set (3 s or off) and the outcome of one fresh SETTINGS read: saved with its duration, or needs a menu save; it never reports the duration from before the write.
- AC-Z39H24.4: A read-only settings-save check reads SETTINGS once and reports saved (with its duration) only when both blocks are valid and bytes 0x1C–0x5B equal the snapshot taken before the logo write, needs a menu save while a block is invalid, and calibration changed when the blocks are valid but those bytes differ.
- AC-Z39H24.5: The wait repeats that check at least 2 s apart on the session clock until saved, calibration changed, the timeout passes or the caller stops it, and sends only SETTINGS reads.
- AC-Z39H24.6: Upload and Remove are refused before anything is sent while the session's SETTINGS read has an invalid block; the refusal and every other invalid-block settings error give the menu-save steps.
- AC-Z39H24.7: Regression: a settings write while block A is stale sends no 0x0A frame and is refused with the menu-save steps; nothing ever writes to repair the block.
- AC-Z39H24.8: Before the confirmation, the logo write and remove commands print the duration now and what the write sets it to.
- AC-Z39H24.9: Regression: after the write the command line prints the startup duration from a fresh read; when the settings need a menu save it prints the steps, waits (default 300 s, set with a timeout option, 0 for no wait), prints the duration once saved and exits 0, exits 6 on a timeout or Ctrl-C and exits 5 when calibration changed.
- AC-Z39H24.10: The settings command, in text and JSON, exits 6 with the menu-save steps when a block is invalid; the raw view still prints the block.
- AC-Z39H24.11: The protocol doc and the command line reference describe 0x1C as the startup duration, the stale check value, the menu save and exit code 6, with the device findings tagged as device facts.

## Technical Design

### Root cause
The vendor app's 0x1C write was read as a separate logo flag. It sets the startup duration, and the firmware does not refresh the block A CRC. The CLI printed the duration from the read before the write.

### Fix
The session snapshots 0x1C..0x5C before the writes, re-reads SETTINGS after them and adds a paced, read-only check and wait. The CLI prints the change before confirming, then the steps, then waits. A stale block maps to exit code 6. The sim freezes CRC A on 0x1C and repairs it on a menu-save event.

## Testing

Mock-transport tests for the result and the check; simulator tests for the stale block, the menu save, the wait and the refused settings write; CLI integration tests for the prompt text, the wait, the timeout and the exit codes.

## Notes

Source: M7C stage 2 and 3 reports, 2026-11-06. No new device path; the 0x1C values stay 0 or 2. A replug with the stale block was never tried, so nothing relies on one.
