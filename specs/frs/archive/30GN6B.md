# The demo meter's menu-save test does not race the runner

## Summary

A desktop test failed on the macOS CI runner because the demo meter had already saved its settings when the test first looked.
The test now accepts a save that came during a long upload, but never one sooner than the demo's delay.
It still checks that the demo meter saves by itself and ends at 3 s.

## Requirement

### Steps to reproduce
1. Run the desktop crate's library tests on a slow runner, where a logo upload and its read-back take longer than 4 s.

### Expected
The demo menu-save test passes on every runner.

### Actual
PR 13 CI run 42351831181, macOS gate: the demo menu-save test failed at logo.rs:1068 with left "saved", right "needs_menu_save".

## Acceptance Criteria

- AC-30GN6B.1: Regression: with the demo's save delay at zero, as on a runner slower than the delay, the demo menu-save test passes; before the fix it failed exactly as on CI.
- AC-30GN6B.2: A "saved" result straight after the upload passes only when the upload took at least the demo's delay; any other state than saved or needs a menu save fails the test.
- AC-30GN6B.3: Either way the test ends with the demo meter's own save and a startup duration of 3 s, and the demo's delay has one named home that the demo device and the test share.

## Technical Design

### Root cause
The demo meter's save timer starts at the 0x1C write, inside the upload. The test assumed the chunks and full read-back finish within the 4 s delay. On the macOS runner they did not, so the fresh check after the write already read "saved".

### Fix
DEMO_MENU_SAVE_AFTER in the devices module holds the delay. The test times the upload and branches on the state it got. No app behaviour changes.

## Testing

The test at the real delay and at a zero delay, the desktop library tests with the e2e feature, clippy and fmt.
