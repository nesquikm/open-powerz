# Detect stopping a PD capture says so

## Summary

Pressing Detect in the Trigger tab stops a running PD capture, because a trigger session needs the meter's PD port.
In the r4 hardware run the PD analyzer then showed nothing about it: Start was simply enabled again.
This fix makes the PD analyzer say why its capture stopped.
The stop itself does not change.

## Requirement

### Steps to reproduce
1. Start a PD capture in the PD analyzer.
2. Open the Trigger tab and press Detect.
3. Go back to the PD analyzer.

### Expected
The PD analyzer says the capture stopped because a trigger session started.

### Actual
No message; the capture looks as if it had never run.

## Acceptance Criteria

- AC-JQ971R.1: When opening a trigger session stops a running PD capture, the backend's capture-stopped event carries the reason "trigger". A stop the user asked for, a disconnect or an unplug carries no reason. Rust tests cover both.
- AC-JQ971R.2: The PD analyzer then shows a notice in its status area: "The PD capture stopped when Detect opened a trigger session. The meter needs a replug before a new capture." The captured rows stay.
- AC-JQ971R.3: The notice goes away when a capture starts again, when a Start is refused (only the refusal shows, unchanged), when the meter disconnects or another meter is shown; a stop the user asked for shows no notice.
- AC-JQ971R.4: Regression: the mock backend stops a running capture with the reason on Detect, Vitest covers the notice clearing on a refused Start, and a WebKit test checks the notice after Detect and its removal on Start.

## Technical Design

### Root cause
The trigger session stops the sniffer through the same stop as the Stop button, so the page cannot tell the two apart.

### Fix
The worker's stop command takes an optional reason that its capture-state event carries, set only by the trigger install path. The page's capture store keeps the reason until the next start or session change, and the analyzer renders the notice from it.

## Testing

Worker tests for the event with and without a reason, Vitest for the store, and a WebKit test on the mock.

## Notes

Source: M7b r4 hardware run, part P2 (also seen in r3). Opening the Trigger tab alone still leaves the capture running; only Detect stops it. [device] After any trigger session closes, the meter refuses a PD capture start until it is replugged (three sightings, r4 and r5); no command works around it.

## Hardware evidence (r4 to r6)

- [x] AC-JQ971R.2: r6 (20e4bb1, 2026-11-05) part D2. Detect stopped a running capture (`pd capture stop accepted`, then `pdm open`), and the PD analyzer showed exactly "The PD capture stopped when Detect opened a trigger session. The meter needs a replug before a new capture." Start was enabled and Stop disabled. Caveat: nothing was on the meter's output, so the capture had 0 rows before and after Detect, and "the captured rows stay" was only seen for an empty table. Vitest and the WebKit spec cover rows with data. (r5 D2 showed the earlier wording.)
- [x] AC-JQ971R.3, the refused-Start and new-start halves: in r6 D3 a Start without a replug was refused and only the refusal banner showed (the D2 notice was gone); in D4, after a replug, the capture started and the banner cleared. The disconnect and other-meter halves are covered by Vitest only.
