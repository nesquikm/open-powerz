# The sub-chart placement test reads both boxes once the layout has settled

## Summary

A chart test failed on a macOS runner while the sub-chart sat below the main plot in every frame.
When the sub-chart appears, the main plot shrinks over a few frames to make room.
The test read the plot's box and the sub-chart's box at two different moments.
So it paired the plot's old bottom edge with the sub-chart's new top edge and saw an overlap that never existed.
It now waits for the layout to settle and reads both boxes at once.

## Requirement

### Steps to reproduce
1. Run the chart ruler spec on a slow macOS runner.

### Expected
The check that the sub-chart is below the main plot passes.

### Actual
PR 12 CI run 2 on 2d3c4ca, macOS shard 1: the sub-chart's top was read 8 to 12 px above the plot's bottom, on both attempts.

## Acceptance Criteria

- AC-82AH25.1: Regression: the sub-chart test reads the main plot's bottom and the sub-chart's top in one page call, after the layout has stopped changing, and still requires the sub-chart to start at or below the plot's bottom.
- AC-82AH25.2: A per-frame probe after the sub-chart is turned on finds it 8 px below the main plot in every frame, in Chromium and WebKit.
- AC-82AH25.3: The chart ruler spec passes three times in a row in both browsers with no retries.

## Technical Design

### Root cause
Two awaited `boundingBox` calls a frame or more apart, while the plot's resize waits for the next animation frame and settles over about five frames.

### Fix
The shared `settled` helper and one `evaluate` that reads both rectangles. No app code changes.

## Testing

The probe in both browsers; the chart ruler spec three times per browser; the full gate.
