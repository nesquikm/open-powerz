# An unasked PD offer list does not refresh the ready offers

## Summary

During protocol triggering, a charger can send a new offer list without being asked.
The safety check above 5 volts used that list.
Requests were still checked against the list from the last negotiation.
Now a new list that arrives while PD is ready replaces those offers.
An empty list makes the next request enter PD again first.

## Requirement

### Steps to reproduce
1. Enter PD in a trigger session and let it negotiate.
2. Let the charger send another offer list unasked, then request a position.

### Expected
The request is checked against the newest list.

### Actual
It is checked against the list from the negotiation (v0.12.0 advisory on AHTZW4).

## Acceptance Criteria

- AC-3B70SA.1: Regression: an offer list that arrives unasked while PD is ready replaces the ready offers, and a position only the new list lacks is refused before anything is written.
- AC-3B70SA.2: While PD is not ready, an unasked offer list updates the capabilities only and PD stays not ready.
- AC-3B70SA.3: An unasked offer list with no usable offer leaves PD not ready, so the next request enters PD again before it writes anything.

## Technical Design

### Root cause
The reply reader updates the capabilities on every block, but the ready offers are set only at the end of a negotiation.

### Fix
When the reader takes a PD offer block while PD is ready, it sets the ready offers from the updated capabilities, or clears them when there are none.

## Testing

powerz-protocol tests over a scripted port; the trigger engine tests stay green.

## Notes

Advisory from the AHTZW4 audit; small and safe, so fixed rather than noted.
