# The firmware Device list line keeps noting the meter after the update ends

## Summary

On the real meter the Device list line stopped at the bootloader label.
The update ended a moment before the system listed the meter in application mode again.
The app only noted the device list while the update ran, so it missed that last listing.
After this fix the app keeps noting the updated meter once the update ends.
It stops when the meter is back in application mode or when the outcome is closed.

## Requirement

### Steps to reproduce
1. Connect a KM003C in application mode, turn Hide serial numbers off, and open the Firmware view.
2. Choose a firmware file, confirm its version and start the update.
3. Wait for "The meter was updated to 2.0.7." and read the Update progress section.

### Expected
The line reads "Device list: KM003C — serial → KM003C — serial (bootloader mode) → KM003C — serial", three labels, until Close.

### Actual
r5 Part F3 (M7B-r5-20261104-1933): the line kept two labels, ending with "(bootloader mode)", also 1.5 minutes later. The app log shows "bootloader to application" and "connected" in the same second the update ended.

## Acceptance Criteria

- AC-PGY704.1: Regression: `apps/desktop/src/lib/firmwareUpdate.listedHistory.svelte.test.ts` › `a meter listed back in application mode after the update ended completes the line` fails before the fix and passes after it: an update that ends done while the meter is still listed in bootloader mode, then a listing in application mode, gives three labels.
- AC-PGY704.2: After an update ends (done, failed or stopped), the updated meter's listings keep joining the line until a label in application mode closes it, and the line is unchanged by any list that comes after that.
- AC-PGY704.3: Once the outcome is closed, no listing is noted, and the line stays empty until a new update starts.
- AC-PGY704.4: Regression: `apps/desktop/e2e/ui/firmware-device-list.spec.ts` › `a relisting that arrives after the update ended still adds the third label` fails before the fix and passes after it on WebKit: a mock update in which the meter is listed in application mode again only after the update has ended shows three labels, with the switch off and on.

## Technical Design

### Root cause
`App.svelte` notes the device list only while `firmware.busy`, and `noteListings` in `firmwareUpdate.svelte.ts` returns when the update is not busy. The real backend ends the flash before the OS lists the meter in application mode again, so that listing is dropped. The mock relisted before the update ended, so tests passed.

### Fix
The store exposes a reactive getter, true while an update runs and, after it ends, until the line's last label is in application mode; dismiss and a new start reset it. The app's effect and `noteListings` both use it. The mock gains a replug variant that relists after the flash resolves.

## Testing

Vitest on the store with fed listings, covering done, failed and stopped endings, the stop rule and Close. One WebKit test on the late-relisting mock, with the switch off and on.

## Notes

Source: M7b r5 hardware run, part F3. It completes XCCQAK on hardware; the r6 re-check reads the line again.
